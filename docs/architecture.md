# Architecture

## Database layout (Postgres 15, database `test_crm`)

| Schema | Contents |
|---|---|
| `meta` | Registry (`pc_0001` objects, `pc_0002` properties, `pc_0003` property options, `pc_0004` association labels, `pc_0007` currencies with current exchange rates) with friendly views (`meta.objects`, ...), `schema_changes`, `record_history`, `currency_rates`, `currency_settings`, `calc_dependencies`, `calc_queue`, `import_jobs`, `migrations`, and the rule-enforcing functions |
| `crm` | One table per object, named by code (`crm.pc_0010`), plus a friendly view per object (`crm.contacts`); `crm.pc_0005` associations with views `crm.associations` and `crm.associations_both` |
| `reporting` | Active-rows-only views per object, plus registry views. The only schema the AI reporting role can read (besides `integrations`) |
| `integrations` | Synced outside data, created by `meta.create_integration_table` |
| `view_data` | Custom view queries read only this: one view per object (active rows, same shape as `reporting.<object>`), owned by `test_crm_view_reader` so row-level security applies, plus `associations` and registry views (migration 0030) |
| `rls` | Helpers for the row-level security policies (setting readers, `rls.shared_ids`, `rls.option_labels`) |
| `auth` | API keys, identities (Google, Microsoft, magic link, passkey), passkeys, magic links, sessions, roles and permissions |

### Base columns on every object table

`object_type_id`, `pc_xxxx_id` (PK, 10-char hex), `name`, `created_at` (user-changeable), `updated_at` (generated copy of `row_updated_at`), `merged_ids`, `merged_into_id`, `record_status` (`active`, `archived`, `merged`, `deleted`), `row_created_at`, `row_updated_at`, `created_by`, `updated_by`. `created_by` and `updated_by` are also read-only properties of type `actor` ("Created by", "Updated by", migration 0049), shown in `crm.<api_name>`, `reporting.*` and `view_data.*` right after `record_status`; history never records them.

Triggers on every object table:
- `before_write`: blocks changes to ids and creation timestamps, bumps `row_updated_at`, stamps `updated_by` from `crm.actor`.
- `after_write`: writes per-property history, queues calculations that read the changed columns.
- History rows also carry `channel` (`crm_ui` for a browser session, `api` for an API key or an OAuth app on /v1, `mcp` for the MCP server) and `api_key_id`, taken as column defaults from `crm.channel` / `crm.api_key_id`, which `withTx` sets when given the caller's principal (`withTx({ principal: p })`, `channelOf` in `api/src/db.ts`; migration 0043). Fixed principals (public pages, booking, payments) and jobs leave them null. `GET /v1/objects/{object}/{id}/history` derives `via` (`calculation` when the source is a calculation, else the channel; rows from before 0043 fall back to `mcp` by source and `api` for `api:<prefix>` actors, everything else is `other`), adds `changed_by_name` and `api_key_name` (old `api:<prefix>` rows find their key by prefix), filters by `property`, `changed_by` and `via`, and returns `facets` for the filter menus. The id column (`<code>_id`, "Record ID") is never written to the history, so the endpoint adds a row for it made from the record's first `created_at` row (same time, author and channel); records created with history off have none.

### Associations

One row per link in `crm.pc_0005` (`label_id`, `from_object_type`, `from_id`, `to_object_type`, `to_id`). The label (`meta.pc_0004`) fixes the direction: from the from-record the to-record is `label`; from the to-record the from-record is `inverse_label`. Each object pair also gets a default unlabeled type on first use. Same-object default and symmetric labels store the smaller id first so a pair cannot be saved twice.

Two covering indexes, one per end. `crm.associations_both` is a `union all` of each row as-is and flipped; filtering on `(object_type_id, record_id)` uses a separate index in each branch. Cardinality limits (`max_to_per_from`, `max_from_per_to`) are checked on insert (for example, a line item has at most one Product).

Which objects may be linked at all is fixed by `meta.association_allowed(a, b)` (migration 0016), checked by `check_allowed` triggers when a label is created (so blocked pairs never get a default label) and when a link is inserted. Every pair is allowed except: users link only to teams; email templates link to nothing; lines link only to products and to line parents (deals, quotes, invoices, payments, carts, orders and custom objects; migration 0028, see "Line items"); calls, emails, notes and tasks do not link to each other, nor to lines, forms, marketing events and participations, object events and occurrences, carts, quotes, payments or invoices. `meta.association_system_only(a, b)` names allowed pairs only the system links: forms and form submissions (linked when a form is submitted), and calls and booking pages (linked when a meeting is booked, migration 0022). The API refuses to create or delete those links for callers (`assertUserLinkable` in `api/src/records.ts`, on the association PUT/DELETE routes and on record create with `associations`); the public submission path calls `createRecord` directly. `GET /v1/schema` returns `links_to` and `system_links` (api names) per object; the UI uses them for association cards, association columns, activity tabs and the note box.

### Line items

Migration 0028. A line (`pc_0020`) links to at most one product and at most one parent (`meta.is_line_parent`: deals, quotes, invoices, payments, carts, orders, custom objects), whatever the label; the `line_links` trigger on `crm.pc_0005` refuses a second one (a parent that was merged away does not count, so merging a parent moves its lines to the winner). A line without a parent is allowed (made from the Lines table or the API). Archiving a parent archives its active lines (history source `parent_archived`); restoring it restores only lines whose latest status change has that source, so a line archived on its own stays archived. Permanently deleting a parent deletes its lines (`meta.set_record_status` and `meta.delete_record` were replaced). The cascade ignores the caller's permissions on lines.

`meta.copy_lines(from_object, from_id, to_object, to_id)` copies a parent's active lines onto another parent in creation order: name, product link (same label) and every property except unique, read-only and calculated ones, which start blank. API: `POST /v1/objects/{object}/{id}/lines/copy` `{from_object, from_id}` (edit on the target, read on the source, create on lines; returns `{copied, ids}`).

UI: the Line items card's + (on every object that can hold lines) opens the line items editor (`web/src/components/LineItemsEditor.tsx`): all the parent's lines in a grid, product lines picked by product search (name, SKU, unit price, unit cost and unit of measure come from the product and the line links to it) and custom lines from the Add custom line dialog (`line_type` `custom`, `customizations`, optionally linked to the product they are a variation of; migration 0054), saved together with Save. The Lines table's Create button opens "Add line item" (`web/src/components/AddLineModal.tsx`) without a parent. A deal's Quotes and Invoices cards offer "Create quote/invoice" (linked to the deal, with "Copy the deal's N line items", on by default) or linking an existing one. A line's page shows a Belongs to card (the parent, or a picker when it has none) and its Product card. A quote or invoice created from a deal also starts with the deal's amount and currency (a currency the quote or invoice does not offer is left out). Parent amounts follow the lines only on request, for deals, quotes, invoices, carts and orders (`AMOUNT_PARENTS` in `web/src/lib/lines.ts`; not payments or custom objects): adding a line from the parent's card has "Update the deal amount: $X → $Y" (on by default, set from the stored lines after saving); after a save on a line's page that changes its amount, the Belongs to card offers "Update deal amount"; removing a line from the parent's card, archiving a line from its page, editing quantity, unit price or discount in the Lines table (inline or Edit all) and Delete all in the Lines table ask once (a browser confirm listing each parent, old and new amount) for every parent whose amount differs from its active lines' total.

### Publishing and page addresses

Migration 0029. Quotes, invoices, forms and booking pages always have a status (dropdown `default_value` `draft`, see `docs/property-types.md`). The customer link card on their record pages (`web/src/components/PublicLinkCard.tsx`) has a Publish button while the record is a draft: it makes the link if there is none, then sets the quote to `sent`, the invoice to `open`, the form or booking page to `published`. Each of the four can have a `slug` (Page address, lowercase letters, digits and dashes, unique per object, case-insensitive) that works next to the random `public_key` (`/p/quote/#acme-roof`); the public routes find a record by either, a key match first (`byKey` in `api/src/routes/public.ts`), and slugs are cleaned by `cleanSlug` in `api/src/records.ts`. A quote or invoice slug is guessable: anyone who guesses it sees the document, and the card says so. With a slug set the card hides "New link", since the slug keeps working. The create dialog for quotes and invoices asks only name and expiration (quotes) or due date (invoices).

### Roles

| Role | Used by | Can |
|---|---|---|
| `claude_admin` | migrations, support, Claude | owns everything |
| `test_crm_api` (NOLOGIN) | the API (connects as claude_admin, `SET ROLE`) | read `crm`/`meta`, write record columns via per-column grants, call public `meta.*` functions, manage `auth` |
| `test_crm_reader` | `reporting_reader` login (AI reporting) | read `reporting` and `integrations` only |
| `test_crm_view_reader` (NOLOGIN) | custom view queries (the API does `set local role` per query) | read `view_data` (and the `crm` tables under it, filtered by row-level security) |

Base columns other than `name` and `created_at`, and calculation columns, have no write grant, so even a buggy API cannot write them.

### Row-level security (migration 0030)

Every object table has row-level security with two policies (`meta.refresh_rls`, rerun by `meta._refresh_views` on every schema change): `everyone_else` lets every role but `test_crm_view_reader` see all rows (nothing changed for the API, reporting or owners), and `view_reader_read` repeats `recordFilter` (`api/src/auth.ts`) for `test_crm_view_reader` from per-transaction settings the API sets: `pcrm.access` (`all` or `restricted`; anything else, including unset, means no rows), `pcrm.owner_ids` (own or team user ids, matched against `owner`, or `created_by` when the object has no owner dropdown) and `pcrm.rule_ids` (the viewer's sharing rules). Shared records come from `rls.shared_ids(code)` (security definer, once per query), which compiles each rule with `meta.compile_filter_groups`, a SQL port of the search filter compiler (a rule that no longer compiles grants nothing, as in the API). Users (`pc_0000`) are visible to any restricted viewer, as in `recordFilter`. Policies read only `owner`/`created_by`, so archiving and deleting other properties is not blocked; deleting an archived `owner` property would be. The `view_data` views are owned by `test_crm_view_reader` rather than `security_invoker` (local tests run on Postgres 14). For now only view queries run under these policies; switching the API itself to them is the next step in `docs/tenant-isolation.md` section 5. Known gap: `view_data.associations` is not filtered, so a view can see the ids (not the data) of linked records the viewer cannot read.

Route layout (`{object}` is an api_name like `contacts` or a code like `pc_0010`):
- `/v1/schema`, `/v1/schema/{object}`: object definitions
- `/v1/schema/{object}/properties[/{property}[/options[/{value}]]]`: properties and dropdown options
- `/v1/objects/{object}[/{id}]`: record CRUD, plus `/search`, `/batch`, `/batch/read`, `/bulk/update`, `/bulk/archive`, `/bulk/restore`, `/merge`, `/imports`, `/exports`, and per record `/history`, `/restore`, `/permanently-delete`, `/associations[/{toObject}/{toId}]`
- Bulk edits (`bulkUpdateRecords` in `src/records.ts`): `POST /v1/objects/{object}/bulk/update` `{ids, properties, modes?}` sets the same values on up to 500 records, each through `updateRecord` (same access, hooks and checks as a single edit), all or nothing. Unique properties are refused (400, `details.property`). `modes` is per multi-choice dropdown: `append` adds the given choices to each record's own, `remove` takes them away, `replace` (default, the only mode for other types) overwrites. `POST /v1/objects/{object}/bulk/archive` `{ids}` archives up to 500 records like `DELETE` (needs delete permission and delete access to every record). The table page uses both: a checkbox column (header box ticks every row shown, shift-click ticks a range), then Edit all (one property; unique and non-editable ones are not offered) or Delete all (archives), sent 500 ids per call.
- Reads can include associated records: on `GET /v1/objects/{object}/{id}` with `?associations=companies,deals&association_properties=companies:name,companies:domain`; on `/batch/read` with `"associations": [{"object": "companies", "properties": ["name"], "limit": 100}]`. Without properties only ids and labels come back. Only active associated records the caller can read are included, 100 per object per record by default (max 500).
- `/v1/users/{id}/roles` (anyone who can read users; direct roles and roles through teams), `/v1/users/{id}/sign-ins` (admins or the user themself: linked sign-in accounts and the last 100 sessions with IP, user agent and status) in `src/routes/users.ts`
- `/v1/association-labels`, `/v1/schema-changes`, `/v1/api-keys`, `/v1/roles`, `/v1/currencies`, `/v1/currency-settings`, `/v1/currency-rates`, `/v1/integrations`, `/v1/imports/{id}`

Two credentials are accepted, both as `Authorization: Bearer`: API keys (`pcrm_<prefix>_<secret>`, below), meant for an admin's own scripts and jobs, and OAuth access tokens (`pcrm_at_...`, see "OAuth and MCP"), meant for apps a user connects. Both stay; the API docs page opens with a guide to choosing between them (`AUTH_GUIDE` in `src/openapi.ts`).

Scopes: `read`, `write` (records, associations, imports), `schema` (objects, properties, options, labels, integration tables), `admin` (everything, plus keys, roles, permanent deletes). New keys (API, `POST /v1/api-keys`, and the CLI) must belong to an active user and expire after 90, 180 or 365 days (default 90; an exact `expires_at` up to a year away also works); the admin scope needs a user with an admin role. `POST /v1/api-keys/{id}/rotate` issues a replacement with the same name, user and scopes and ends the old key after `grace_hours` (default 24). `auth.api_keys.last_used_ip` and `replaced_by` come from migration 0019. The CLI's `--bootstrap` makes a userless admin key that lasts 24 hours, for a database with no users yet. Older keys without a user or expiry keep working until revoked. Keys linked to a user are further limited by that user's roles, and an admin-scope key whose user no longer has an admin role loses the admin scope (direct or through teams; most permissive role wins; `is_admin` roles are unrestricted). Record access `own`/`team` filters by the `owner` dropdown, or by `created_by` on objects without one; users have no owner, so record access and sharing rules do not apply to them and the role's object permissions alone decide. Sharing rules (migration 0012, `auth.role_sharing_rules` plus `auth.role_sharing_rule_associations`) widen that: a rule shares the records of one object that match `filter_groups` (the search filter format), at `read` or `edit`, and optionally the records linked to them (one hop, any label or one label, each `read` or `edit`). `recordFilter` in `src/auth.ts` ORs the rules of all the user's roles into the own/team clause, by `AccessMode`: `read` uses every rule, `edit` (updates, association writes) only edit rules and links, `delete` (archive, restore, merge) ignores rules. Rules never grant object permissions, so the role still needs Read/Edit on the object. Rules are live (a record that stops matching drops out at once); a rule whose filter no longer compiles (say its property was archived) grants nothing and `GET /v1/roles/{id}/sharing-rules` reports it as `problem`. Rule filters ignore hidden-property settings. Admin endpoints: `/v1/roles/{id}/sharing-rules` (GET, POST), `/{ruleId}` (PUT replaces, DELETE), `/preview` (POST, counts per object). Roles with record access `all` skip rules. A user with no role can sign in but sees nothing (the UI home page says so). Role changes that would leave no active user with an admin role (removing an assignment, deleting a role, turning off `is_admin`) are refused with 400; this only applies once at least one such user exists, and admin-scope API keys do not count. Deactivating, archiving, merging or deleting the last such admin user is refused by the trigger `keep_an_admin` on `crm.pc_0000` (migration 0011, `check_violation`, so 400 `rule_violation` from the API), whatever path the change comes from. Both guards use `meta.has_active_admin()`. Known gap: removing the last admin from an admin team (deleting the user-team association) is not blocked.

### Security log (`src/audit.ts`, migration 0019)

`auth.security_events` records sign-ins (`sign_in`, `sign_in.failed` with provider, reason and email), `sign_out`, `session.revoked`, `api_key.created|revoked|rotated`, `role.created|updated|deleted|object_permission|property_permission|assigned|unassigned`, `sharing_rule.created|updated|deleted`, `settings.updated`, `export` and `oauth.client_registered|authorized|denied|revoked|token_reuse|app_blocked|app_unblocked`, with actor, the user concerned, IP, user agent, target and details. `test_crm_api` has only SELECT and INSERT on it, so the API cannot change or delete entries. `GET /v1/security-events` (admin; `limit`, `before`, `user_id`, `event` which also matches a group like `api_key`) feeds Settings → Security log. Failed API-key attempts are not logged (anyone can send them; nginx rate limits handle floods). No retention limit yet.

### Security headers

Every API response carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` and a CSP (`default-src 'none'; frame-ancestors 'none'` on JSON, `frame-ancestors 'none'` on the docs page and PDFs), plus HSTS over https (`onSend` hook in `src/server.ts`). The built web pages carry a CSP `<meta>` tag (`csp()` in `web/vite.config.ts`): scripts only from the site, requests only to the site and `VITE_API_URL`, images from any https site (custom form HTML). Not applied by the dev server, which needs inline scripts.

### Google & Microsoft sign-in (`src/sso.ts`)

Microsoft accounts are linked to a CRM user on their first sign-in by the `upn` claim (Entra only allows UPN domains the tenant has verified, or its `.onmicrosoft.com`), else the `email` claim (left out for unverified addresses on app registrations made after June 2023). `preferred_username` can be changed by the account's tenant, so it is never used to link (the "nOAuth" takeover); without `upn` or `email` a first sign-in is refused with `no_verified_email`. After linking, the account is matched by `sub` in `auth.identities`.

OpenID Connect authorization code flow with PKCE, no extra dependencies:
1. The UI links to `GET /v1/auth/{google|microsoft}/start?return_to=/path`. The API puts state, PKCE verifier, nonce and return path in a 10-minute HttpOnly cookie (`pcrm_google` or `pcrm_ms`, path limited to the callback) and redirects to Google or Microsoft.
2. The provider redirects to `GET /v1/auth/{google|microsoft}/callback`. The API checks the state against the cookie, exchanges the code (with client secret and verifier), and validates the ID token's claims (`iss`, `aud`, `exp`, `nonce`, email, and subject).
3. The user is found by `auth.identities` (provider `google` or `microsoft`, provider subject) or, the first time, by an active user record whose email matches (case-insensitive); that link is then saved. No match means no sign-in (no self sign-up). A user whose Status is `deactivated` is refused (`auth_error=user_deactivated`).
4. A random session token goes in `auth.sessions` (sha256 stored) and in the session cookie (HttpOnly, SameSite=Lax), and the browser is sent back to the UI. Over https the cookie is `__Host-pcrm_session` (Secure, Path=/, no Domain, so a sibling `*.profitpad.com` site cannot set or overwrite it); over plain http (local dev) it is `pcrm_session`. Signing in again from the same browser revokes that browser's previous session. Errors come back as `?auth_error=<code>`.

Who may sign in is one SQL predicate, `USER_CAN_SIGN_IN` in `src/auth.ts`: the user record is `record_status = 'active'` and its `status` dropdown is not `deactivated` (empty counts as active). It is checked at sign-in, on every session request (so deactivating someone ends their sessions at once), for API keys linked to a user, and by the last-admin guard. Session principals act as their user: an admin role gives the `admin` scope, anyone else gets `read` and `write`, limited by their roles. Because cookies are sent from any `*.profitpad.com` page, POST/PUT/PATCH/DELETE with a cookie must carry an `Origin` that is in `CORS_ORIGINS` or is the API's own origin. `POST /v1/auth/logout` revokes the session.

Session limits (`SESSION_POLICY` in `src/auth.ts`, migration 0019 adds `auth.sessions.last_seen_at`): users are signed out after 7 days without a request or 30 days after signing in; users with an admin role after 24 hours idle or 7 days. A session found past its limit gets `expires_at = now()` so the history shows it as expired; `last_seen_at` is written at most once a minute. Admin changes from a browser session (API keys, roles and their permissions and assignments, sharing rules, ending another user's sessions, webhooks, view integrations, payment settings, OAuth app changes) need a sign-in within the last 4 hours (`requireRecentSignIn`, `REAUTH_HOURS`, always checked before anything is written); otherwise the API answers 403 `reauth_required`. The UI keeps the page as it is: `api()` in `web/src/lib/api.ts` waits on `requestReauth()` (`web/src/lib/reauth.ts`), the app shows "Confirm it's you" over the page, and its sign-in buttons open the provider in a popup that returns to `web/public/signed-in.html`, which reports back over `BroadcastChannel('pcrm-auth')` (the storage event as a fallback; the providers' pages cut `window.opener`) and closes. The waiting requests are then sent once more, so the change is saved without retyping; Cancel throws the original error, and requests that hit the check together share one sign-in. If the browser blocks the popup, the button signs in with the whole page as before (what was typed is lost). API keys are exempt. `GET /v1/users/{id}/sign-ins` reports each session's effective end and `current`; `DELETE /v1/users/{id}/sessions/{sessionId}` ends one session and `POST /v1/users/{id}/sessions/revoke` (`keep_current`) ends all, for the user themself or an admin. `GET /v1/auth/config` tells the UI which providers are configured (`google`, `microsoft`) and gives the portal's `logo` (public, for the login page). An `Authorization` header always wins over the cookie.

Settings (API env): `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, optional `GOOGLE_ALLOWED_DOMAINS`; `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, optional `MICROSOFT_TENANT` (default `common`), optional `MICROSOFT_ALLOWED_DOMAINS`; `PUBLIC_API_URL` (the API's address as browsers see it; the redirect URIs are `<PUBLIC_API_URL>/v1/auth/{google|microsoft}/callback`) and `UI_URL`. Both URLs default to the request's own origin, which fits local dev behind the Vite proxy (`http://localhost:5173`).

Docs: `GET /v1/openapi.json` and `GET /docs` (Scalar, restyled ReadMe-like via `src/docs-theme.ts`, which only overrides Scalar's CSS variables). Public only when `DOCS_PUBLIC=true`.

### OAuth and MCP (`src/oauth.ts`, `src/mcp.ts`, migration 0020)

Apps such as Claude or ChatGPT connect as one user through OAuth 2.1, following the MCP authorization spec revision 2026-07-28 (checked 2026-11-01). The API is both the authorization server (issuer = `PUBLIC_API_URL`) and the protected resource.

- Discovery: `/.well-known/oauth-authorization-server` (RFC 8414; S256 PKCE, `client_id_metadata_document_supported`, `authorization_response_iss_parameter_supported`), `/.well-known/oauth-protected-resource/mcp` (RFC 9728, resource `<api>/mcp`) and `/.well-known/oauth-protected-resource` (resource `<api>`, the REST API). `/mcp` answers 401 with `WWW-Authenticate: Bearer resource_metadata="...", scope="read write"`.
- Clients (`auth.oauth_clients`), all public (no secrets, `token_endpoint_auth_method` `none`): Client ID Metadata Documents (the client_id is an https URL; the API fetches the JSON over https only, 5 s timeout, 10 KB, no redirects, never to private/loopback/link-local addresses (checked on the connection's own DNS lookup), caches it for its `max-age` within 5 minutes to 1 day, and requires `client_id` to equal the URL) or Dynamic Client Registration (`POST /oauth/register`, deprecated in MCP but still used by older clients; ids `pcrm_c_...`, names unverified). Redirect URIs must be https or http on localhost/127.0.0.1/[::1]; they match exactly, except loopback ports (RFC 8252).
- `GET /oauth/authorize` is a page served by the API (on the API host, so the session cookie applies). Bad client or redirect URI: an error page, never a redirect. Other errors go back to the app with `error`, `state` and `iss`. Without a session it shows "Log in with Microsoft/Google" links whose `return_to` is the authorize URL (`toUi` in `src/sso.ts` sends `/oauth/` paths to the API instead of the UI). The consent page shows the app name, who vouches for it (the metadata document's host, or "unverified"), the redirect host, a warning when the app only returns to localhost, and the scopes; the user can untick write. Consent is asked every time. The form posts back to `POST /oauth/authorize` with a CSRF value derived from the session cookie, and the session check also requires the API's own `Origin`.
- Grants (`auth.oauth_grants`): one live grant per user and app, holding the allowed scopes; revoking it ends all its tokens. Codes (`auth.oauth_codes`): single use, 10 minutes, bound to the PKCE challenge, redirect URI and resource; a code used twice revokes the tokens issued for it. Tokens (`auth.oauth_tokens`, sha256 stored): access `pcrm_at_...` for 1 hour; refresh `pcrm_rt_...` for 30 days (7 days for users with an admin role), rotated on every use; reusing a rotated refresh token revokes the whole chain (`family_id`) and logs `oauth.token_reuse`. `POST /oauth/revoke` (RFC 7009) revokes a token (a refresh token takes its chain with it).
- Scopes are `read`, `write` and `schema` (migration 0032). `schema` is offered on the consent page only to users with an admin role and is dropped from a token as soon as its user loses the role; it allows custom views and the property tools. A token acts as its user (`authenticateOAuthToken` in `src/auth.ts`): roles, record access and hidden properties apply as in the UI, and apps never get `admin`. Connections made before 0032 keep read and write; reconnect to add `schema`. A token works only at the resource it was issued for (RFC 8707 `resource`, default `<api>/mcp`): MCP tokens are refused by `/v1`, and `<api>` tokens by `/mcp`. Tokens stop at once when the user is deactivated, the grant is revoked or the app is blocked.
- `/mcp` (Streamable HTTP, `@modelcontextprotocol/server` 2.4.0, `createMcpHandler`, stateless): serves 2026-07-28 clients and older 2025 clients (stateless legacy fallback) from one server definition, built per request for the token's user. Tools: `list_objects`, `describe_object`, `search_records`, `get_record` (read) and `create_record`, `update_record`, `link_records` (write; a read-only token gets a 403 `insufficient_scope` challenge so the client can ask for more). API errors come back as tool errors (`isError`). Writes go through the same record functions as `/v1` and are recorded with `crm.source = 'mcp'`. Requests with a browser `Origin` are refused unless it is in `MCP_ALLOWED_ORIGINS`. API keys are not accepted at `/mcp`. With the `schema` scope the server also registers the custom view tools (see Custom views) and the property tools `create_property`, `update_property`, `archive_property`, `unarchive_property`, `add_dropdown_option`, `update_dropdown_option`, `archive_dropdown_option`, `unarchive_dropdown_option`, `test_calculation` (the same functions as `/v1/schema`, exported from `src/routes/schema.ts`; recorded with `crm.source = 'mcp'`), and its instructions point the model at `view_guide`. No delete tools.
- Management: `GET /v1/oauth/connections` (own; `?all=true` for admins), `DELETE /v1/oauth/connections/{id}` (own, or admin with a recent sign-in), `GET /v1/oauth/apps` and `POST /v1/oauth/apps/{id}/block|unblock` (admin, recent sign-in). OAuth tokens cannot call these. UI: Settings → Connected apps (everyone: the MCP address to copy and their own connections; admins: everyone's connections and the app list with Block).
- The MCP server info carries `title` "ProfitPad CRM", `websiteUrl` (`UI_URL`) and `icons` (the SVG and a 512px PNG on the API host). Which of these, or the domain's `/favicon.ico`, a given client shows is up to the client.
- Settings (API env): `PUBLIC_API_URL` (also the issuer and the base of both resources), optional `MCP_ALLOWED_ORIGINS`. `OAUTH_INSECURE_METADATA_FETCH=true` allows metadata documents over http and on private addresses, for local tests only; never set it on the server.

### Custom views (`src/views.ts`, `src/routes/views.ts`, `src/views-guide.ts`, migrations 0030 to 0032, 0034, 0035)

Pages admins build through their AI, with no deploy. A view is a record of the native object `views` (`pc_0055`, links to nothing): `name`, `slug` (page address, required, made from the name when missing), `icon` (a Lucide icon name like `chart-column`, checked against the canonical names in the API's `lucide` package, same version as `lucide-react`; `src/icons.ts`, `GET /v1/ui/icons`), `description`, `status` (draft/published), `audience` (admins/everyone), `draft_source` and `draft_queries` (what is being edited), `source` and `queries` (what people see), `published_at`. The code properties and status are read-only through the record API; only the views API writes them, after checking.

- Source: one TSX module with a default export, compiled on the server with sucrase 3.35.1 (typescript, jsx automatic, imports to CommonJS) and cached by hash. Only `react`, `@pcrm/view` and `recharts` may be imported.
- Queries: `{"name": {"sql": "...", "params": {"p": "text|number|date|datetime|boolean"}}}`. `:name` placeholders (quote-aware, `::` casts left alone) become typed binds; `:me` is the viewer's user id. `meta.analyze_view_query` checks each one without running it (single SELECT or WITH, `_check_sql_fragment`, only `view_data` relations, unqualified names resolve in `view_data`, and since migration 0034 a function allowlist, `meta._view_function_allowed`: pg_catalog aggregates and window functions, the functions behind operators and casts, and a named list of math, text, date, array and JSON functions; `set_config` and `current_setting` are refused, so a query cannot change the row-level security settings) and returns the objects, columns and output columns, cached per registry version. At run time the caller needs Read on every object read and no hidden property among the columns (403 otherwise); then the query runs in `begin read only`, `set local role test_crm_view_reader`, the `pcrm.*` settings from the caller's roles, a 10 s timeout and at most 5000 rows (`truncated`). bigint and numeric come back as numbers.
- Opening: drafts need the `schema` scope (admins; admin MCP connections); a published view opens for admins, or for everyone with read access when its audience is `everyone`. Rows are always limited by row-level security.
- Endpoints: `GET /v1/views`, `GET /v1/views/{slug}` (compiled module and query names), `GET /v1/views/{slug}/code`, `POST /v1/views/{slug}/queries/{name}` (`?draft=1`), `POST /v1/views`, `PUT /v1/views/{slug}/draft`, `POST /v1/views/{slug}/publish`, `POST /v1/views/{slug}/revert` (draft back to the published version), `POST /v1/views/try-query` (unsaved SQL, 50 rows). `{slug}` also takes the id.
- Browser: `/view/#<slug>?param=value` (`web/src/pages/CustomView.tsx`; admins add `?draft=1` before the hash). The module runs in a sandboxed iframe (`sandbox="allow-scripts"`, opaque origin) loading `/view-frame/index.html`, one self-contained file built by `web/vite.frame.config.ts` from `web/src/view-runtime/` (React, recharts, the `@pcrm/view` kit in `kit.tsx`, Inter fonts inlined; about 1 MB, 390 KB gzipped). Its CSP allows only its own inline script (by hash) plus `unsafe-eval` for the module, and loads nothing from the network (`connect-src 'none'`, `img-src data: blob:`), so a view cannot send data out in a request or an image URL. CSP cannot forbid a frame navigating itself, so the page counts the frame's loads and removes the view on a second one (the first such request still goes out). Record changes from a view (`createRecord`, `updateRecord`, `linkRecords`) wait for the viewer to allow each one in a dialog listing the changes, with "Don't ask again on this page". The page answers the frame's `postMessage` calls (`view-runtime/protocol.ts`): queries through the views API, `openRecord`, `navigate` (CRM paths only), `setParams` (the hash), and `createRecord`/`updateRecord`/`linkRecords` through the record API, all with the viewer's session. The app's CSP now has `frame-src 'self'`. `/reporting` redirects to `/view/#reporting`.
- Icons: menus draw a view's icon with `ViewIcon` (`web/src/lib/lucide-icons.tsx`), which loads the whole Lucide set as one lazy chunk (about 650 KB, 170 KB gzipped) only when some view has an icon; no icon or an unknown one shows `LayoutDashboard`. Admins pick one in the Code card's Icon button (`components/IconPicker.tsx`, searchable grid); the MCP sets it with `create_view`/`update_view_settings` and searches names with `find_icons`.
- `/objects/views` lists them; a view's record page shows the Code card (`web/src/components/ViewCode.tsx`: draft and published React and queries, Open, Open draft, Publish) above the usual activity and Changes tabs.
- Seed views (0031): `reporting` (replaces the mock Reporting page with live counts, money by currency, won by month, open deals by stage, biggest open deals) and `contacts-companies`; both are the examples the guide shows.
- Publishing is the user's call: view output carries `url` and `draft_url` (full links when `UI_URL` is set), `create_view` and `save_view_draft` over MCP add a `next_step` telling the model to give the user the draft link and ask before publishing, and the server instructions, the `publish_view` description and the guide say never to publish unasked.

### Payments (`src/routes/payments.ts`, `src/payments/`, migration 0027)

Customers pay quotes and invoices from their customer link, online through Stripe or by Interac e-Transfer.

- Stripe Connect with Accounts v2, `stripe` 23.0.1 (pins API version `2026-09-30.endive`). ProfitPad's Stripe account is the platform (`STRIPE_SECRET_KEY`). Settings → Payments (`web/src/pages/PaymentSettings.tsx`, admins, recent sign-in) creates the tenant's Stripe account (`POST /v1/payments/stripe/onboard`: `dashboard: full`, merchant configuration with `card_payments`, `fees_collector` and `losses_collector` = `stripe`, so Stripe bills its fees to the tenant and carries losses; no application fee) and sends the admin to Stripe's hosted onboarding (v2 account link, back to `/settings/payments?stripe=return`, or `?stripe=refresh` when the link expired). Only the account id is stored (`auth.payment_connections`, one non-removed row). The account counts as ready when `configuration.merchant.capabilities.card_payments.status` is `active`; it is read again on Settings page load (even when active, since Stripe can still ask for more, such as a selfie check; the page lists what Stripe is waiting for and offers Continue setup on Stripe), on return from Stripe and before each checkout, so there are no account webhooks. `DELETE /v1/payments/connection` stops using it (the Stripe account stays the tenant's).
- Paying: `POST /v1/public/{quotes|invoices}/{key}/pay` creates a Checkout Session as a direct charge on the tenant's account (`Stripe-Account`), one line in the record's currency, `expires_at` 1 hour, and returns its URL; an open session for the same amount is reused (`auth.stripe_checkout_sessions`). Payment methods are dynamic: the tenant turns cards, ACH (US accounts, USD), Canadian pre-authorized debit, Klarna, Affirm, Afterpay and others on in their own Stripe Dashboard. Every session carries the PAD agreement terms (`payment_schedule: interval`, "On completion of checkout", `transaction_type` from settings). Back on the page with `?paid=1` the page polls a few times for the webhook's result, and from the second try asks the API to check with Stripe (below).
- Webhook `POST /v1/stripe/webhook` (auth hook skipped; own Fastify scope with a raw-string JSON parser for the signature; `STRIPE_WEBHOOK_SECRET`). Events are checked against the stored account and `livemode`, then handled once (`auth.stripe_events`) in one transaction: `checkout.session.completed` creates the payment record (pending if `payment_status` is `unpaid`, as for bank debits), `async_payment_succeeded` / `async_payment_failed` settle it, `expired` closes the session, `charge.refunded` (full refunds only) sets `refunded`, `charge.dispute.created` sets `disputed` and `closed` sets `succeeded` (won) or `refunded` (lost). The method used comes from the PaymentIntent (`card`, `ach`, `pad`, `klarna`, else `other`).
- Invoices for paid quotes: when a quote payment succeeds (Stripe or a confirmed e-Transfer, both through `markPaymentSucceeded` in `src/payments/fulfil.ts`), the CRM creates a paid invoice for what was paid: "Deposit for <quote>" for the deposit amount with no lines, or the quote's name for the full amount with the quote's lines copied (`meta.copy_lines`). No invoice number (staff fill it in), due date = the payment date, linked to the quote, the payment and the quote's deals, contacts and companies. The user chose a separate paid deposit invoice (staff invoice the rest) over one part-paid invoice, since invoices are paid in full. A refund or dispute does not change it.
- Missed webhooks: a checkout we have not heard back about (still `open`, or `complete` with its payment still pending) is read from Stripe and applied the same way (`syncCheckouts` in `routes/payments.ts`, sessions from the last 30 days on the current account): `POST /v1/public/{quotes|invoices}/{key}/check-payment` (the page after Checkout), before `/pay` starts a new checkout, and `POST /v1/objects/{quotes|invoices}/{id}/check-payments` (read scope, called by the record page). A delayed method that later fails stays pending until its `async_payment_failed` event arrives. Found in the sandbox test: a real `checkout.session.completed` reached no listener.
- Payment records (`src/payments/fulfil.ts`, principal "Payments") are linked to the quote or invoice and its contacts and companies, with `purpose` (invoice, quote_deposit, quote_full), payer, Stripe ids and `reference`. `markPaymentSucceeded` is the only place a payment changes another record: the invoice becomes `paid`; a quote with Online payment = Without signing that is still `sent` becomes `accepted` with the payer as responder. Refunds and disputes leave the invoice or quote alone.
- Quotes: `online_payment` (off, after signing, without signing), `deposit_type` (none, percent, fixed) and `deposit_value` (`src/payments/amounts.ts`: a deposit of the whole total or more is the full amount; under 0.50 is not offered). After signing means accepted or waiting for a countersignature; without signing also allows a sent quote that has not expired. One payment per quote. Invoices: payable while `open`, full amount (`amount`, else the sum of lines); `/p/invoice/#key` (`web/src/public/invoice.ts`) shows open and paid invoices; `public_key` set like quotes.
- Interac e-Transfer (not in Stripe): `ui.settings` `payments` holds `etransfer {enabled, email, instructions}` and `debit_transaction_type`. The page shows the amount, email and the reference to put in the message ("Invoice INV-1"); "I've sent it" (`POST /v1/public/{object}/{key}/etransfer-sent`) records a pending `etransfer` payment. Staff confirm on the payment's page (`PaymentConfirmCard.tsx`, `POST /v1/objects/payments/{id}/confirm|reject`, needs edit access to the payment).
- While a payment is pending or paid, the page shows that instead of the pay buttons and new payments are refused (409). CAD was added to every currency dropdown. Lines and products still format prices with `currency_code` USD in the CRM (the public pages use the quote's or invoice's currency).

### Public quote and form pages (`src/routes/public.ts`, migration 0013)

Customers open quotes and fill in forms without signing in. The pages are static, on GitHub Pages next to the app, but built from their own Vite entries, so they never load app code: `/p/quote/#<key>` (`web/src/public/quote.ts`), `/p/form/#<key>` (`form.ts`), and `/p/embed.js` for other websites (`embed.ts`, a self-contained IIFE built by `web/vite.embed.config.ts`). They are plain TypeScript with no React. The key sits in the URL fragment, so it never reaches GitHub's or anyone's server logs or referrers. `form-renderer.ts` draws a form from its definition for both the hosted page and the embed, with CSS scoped to `.pcrm-form`.

- Keys: `public_key` on quotes (32 random bytes, base64url) and forms (16 bytes), unique, format checked by the database. Never the record ID. Set by `POST /v1/objects/{quotes|forms}/{id}/public-link` (needs edit access); calling it again regenerates the key, which revokes a quote link or breaks a form's embeds.
- The auth hook skips `/v1/public/`. Those routes look records up by key and write through a fixed principal (`actor` `public`, history source `public_page` / `public_form`) that can only edit quotes and create form submissions.
- Quotes: `GET /v1/public/quotes/{key}` (quote, linked lines, first linked company and contact, theme), `/pdf` (pdfkit, `src/pdf/quote.ts`, drawn like the public page with embedded Inter and Montserrat WOFF files from `@fontsource`), `POST .../accept` and `.../decline` (`{name, email, reason?}`). Only `sent`, `accepted`, `rejected` and `expired` quotes are visible (drafts 404). A sent quote past `expiration_date` shows as expired. Accept/decline work only on a sent, unexpired quote (409 otherwise, checked again under a row lock) and fill `status`, `responded_at`, `responder_name`, `responder_email`, `decline_reason`. Total is `amount`, or the sum of the lines when empty.
- Forms (`src/forms.ts`, migration 0014): `definition` JSON is `{"fields": [...], "submit_label", "success_message"}`, edited with the form builder on the form's record page (`web/src/components/FormBuilder.tsx`, saved through `PUT /v1/objects/forms/{id}/definition`, which checks it strictly). A field is a question of its own (`{name, label, type, required, options?, placeholder?, help?}`, types `text email phone textarea number select multiselect checkbox date datetime`) or a contact or ticket property (`{property: {object, name}}`; key `contact_<name>` / `ticket_<name>`, type and dropdown options taken from the property; user pickers like owner, calculations and files are not allowed). Property fields can be hidden with a fixed `value` (e.g. a ticket's pipeline). Any visible field can have `conditions` (all must hold) on earlier dropdown, checkbox or date fields: `is_any_of`/`is_none_of` option values, `is_checked`/`is_not_checked`, `is_before`/`is_after`/`is_on` a date, `is_empty`/`is_not_empty`. Fields not shown are not required and their answers are dropped (the API re-evaluates; `web/src/public/conditions.ts` mirrors it for the pages). Contact fields need the contact email field, required and always shown: a submission updates the contact with that email (case-insensitive) or creates one. Ticket fields create a new ticket for every submission (named `<form>: <email>` unless the name is a field), linked to the contact. When a property is archived later, its field and the conditions on it drop out of the live form. Only `published` forms are served; the browser never sees hidden fields or property names. `POST /v1/public/forms/{key}/submissions` (`{values, page_url, _hp, _elapsed}`, max 32 KB) needs an `Origin` that is in `CORS_ORIGINS` (the UI, for the hosted page) or in `ui.settings` `forms.allowed_origins` (Settings → Embed domains, admins), else 403. A filled honeypot `_hp` or `_elapsed` under 2 s gets the normal 201 answer but nothing is stored. The submission stores `form_id`, `submitted_at`, `page_url`, `submission_values` (`{key: raw value}`, for automations), `summary` (`[{name, label, value (display text), property?, hidden?}]`, the answers as asked), `origin`, `ip_address`, `user_agent`, and is linked to its form, contact and ticket. Contact and ticket pages show submissions in the activity stream (with the answers); a submission's page shows its answers; a form's page shows the builder and a Form submissions card.
- Form fields, more (migration 0015): text fields can check a `format` (`email`; `phone`: checked by the API with Google's libphonenumber, see Phone numbers below; `url`; or `regex` with `pattern`, matched against the whole answer, and an optional `pattern_message` shown as written); older `type: "email"|"phone"` definitions are read as text with that format, and the contact email always has the email format. On the page, formats are checked when the visitor leaves a field (an error then clears as soon as the answer is valid); phone answers are sent to `POST /v1/public/forms/{key}/phone` (same Origin rule as submissions, 60/min per IP) and, when valid, rewritten as `+1 613-222-0328 ext4`. Any field is prefilled from the page URL's query parameter of the same key (`/p/form/?topic=Sales#key`, or the website's own URL for embeds). A field with `from_url: true` is never shown: its value comes only from that parameter (e.g. `utm_source`); it is never required, cannot have conditions, may drive other fields' conditions, and is checked like any answer. The contact email cannot be `from_url`.
- Custom HTML (migration 0015, forms property `html`): when set, the hosted page and the embed render it instead of generated fields (the builder's "Customize HTML" writes generated markup to start from). Controls are matched by `name` (the field key); `[data-field=key]` is what conditions show and hide; `[data-error=key]` and `[data-error=_form]` are optional error slots. Every write of a form goes through the write hook in `forms.ts` (`onWrite` in `records.ts`, so PATCH, batch and import too): the HTML is cleaned with sanitize-html (no scripts, frames, event handlers, javascript: links or form action; `<style>` is kept, and on an embed it styles the host page too) and checked with htmlparser2 against the definition: one `<form>`, a fitting control for every asked field, a `data-field` wrapper for every field with conditions, a submit button, and no controls named after unknown keys. A builder save that would leave the HTML missing a field is refused the same way.
- The Origin allowlist only stops other websites' pages from posting a form in a visitor's browser; scripts can fake `Origin`. Spam protection is the honeypot, the fill time, validation and rate limits: in-memory per IP in the API (form posts 10/min, quote accept/decline 10/min, reads 60 to 120/min) plus nginx `limit_req` (`docs/deploy.md`). `req.ip` is only the real client behind nginx with `TRUST_PROXY=true`.
- CORS: `server.ts` registers `@fastify/cors` with a delegator: `/v1/public/` routes allow the UI and the allowlist, without credentials; everything else keeps the app's rules (`CORS_ORIGINS`, credentials). The allowlist is cached 30 s and cleared when Settings → Embed domains saves.
- Quote responses show in the activity stream of the quote and of every record linked to it ("Quote accepted" / "Quote declined", from `responded_at` and `responder_*`; nothing extra is stored). Line item cards on record pages show quantity and extended amount ("x2  $24.68").
- Staff UI: the "Customer link" / "Public form" card on quote and form record pages (`web/src/components/PublicLinkCard.tsx`: link, copy, open, new key, PDF, embed snippet) and Settings → Embed domains.
- Quote signing (migration 0018): accepting needs a drawn signature (`signature_png`, a PNG data URL from a 520 x 160 canvas, at most 200 KB, checked for the PNG header; accept body limit 320 KB) and answers to the quote's `signing_fields` (`fields`, `{key: value}`; required fields enforced, `email` and `date` types checked, unknown keys dropped). `signing_fields` is a JSON array of `{key, label, type: text|email|date, required}` (at most 20, keys `^[a-z0-9_]{1,64}$`, unique), checked by the quotes write hook in `public.ts` on every write and stored normalized; staff edit it in the Signing card. Accept stores `customer_signature`, `customer_signed_at`, `customer_ip` (never sent to the public page) and `signed_fields` (JSON). When `requires_countersign` is Yes (a single-value true/false dropdown), the quote goes to `pending_countersign` ("Awaiting countersignature" for the customer) without `responded_at`; staff then countersign with `POST /v1/objects/quotes/{id}/countersign` (`{name, signature_png}`, needs edit access, 409 unless pending), which sets `accepted`, `responded_at`, `countersigner_name`, `countersigner_signature`, `countersigned_at`. Otherwise accept sets `accepted` at once. The public page prefills name, email and signing fields from `?name=`, `?email=`, `?<field key>=`; the page and PDF show both signatures and the signed fields. Drawing code is shared (`web/src/public/signature-pad.ts`, pointer events). Staff UI: `web/src/components/QuoteSigningCard.tsx` (signing fields JSON, signatures, Countersign dialog); the activity stream shows "Quote signed" while pending and "Countersigned by" on accepted quotes.

### Quote document (`src/quote-document.ts`, Settings → Quote document)

What a quote's PDF and public page show beyond the fixed parts (title, status, parties, lines, total, notes, signatures). Stored as JSON in `ui.settings` key `quote_document`; no migration. Admins edit it in Settings → Quote document (`web/src/pages/QuoteDocumentSettings.tsx`); a package installer writes the same JSON with `PUT /v1/ui/settings/quote_document` (admin), checked by `validateQuoteDocument` against the registry (400 with a message naming the item). Nothing saved gives the default layout, which draws exactly as before (checked pixel for pixel on a sample PDF); `line_columns: null` keeps the default columns.

```json
{
  "orientation": "portrait",
  "item_label": null, "item_width": 34,
  "line_columns": [
    {"property": "quantity"}, {"property": "unit_price"},
    {"property": "berry_compliant", "label": "Berry", "width": 8},
    {"property": "lead_time", "width": 12}, {"property": "amount"}
  ],
  "fields": [
    {"property": "payment_terms", "place": "details"},
    {"property": "special_terms", "label": "Notes and special terms", "place": "terms"}
  ],
  "terms_title": "Terms and conditions",
  "tables": [
    {"title": "Kit contents", "object": "kit_items", "columns": [{"property": "name"}, {"property": "quantity", "width": 8}],
     "sort": {"property": "name", "direction": "asc"}}
  ]
}
```

- `line_columns`: line (`pc_0020`) properties after the item column (name with the SKU under it, always first; `name` and `sku` are refused as columns). `quantity`, `unit_price`, `discount` and `amount` are the built-in columns: default labels Qty, Unit price, Discount, Amount and widths 10/17/15/18, money in the quote's currency, discount blank when 0, amount bold; leave one out to hide it. Widths are shares (1 to 100) of the table, item default 40, other columns 12. At most 12 columns.
- `fields`: quote properties, `place` `details` (a label-over-value grid under the parties; multi-line text gets a full row) or `terms` (after the total under `terms_title`, default "Terms", label and value side by side). Empty values are left out. At most 40.
- `tables`: up to 4 tables of records linked to the quote (`object` must be in quotes' `links_to`), drawn after the terms, at most 10 columns and 200 rows each, ordered by `sort` then id. A quote with no such linked records leaves the table out. This is where a bill of materials goes once kit records exist: link them to the quote and add a table.
- Never showable: `public_key`, signatures, `signing_fields`, `signed_fields`, `customer_ip`, `responder_email`, and file, id and id_list properties. Properties are referenced by `api_name`; one renamed or archived later is skipped when drawing and shown as Missing in Settings (rename_property does not rewrite this setting).
- Values are formatted on the API (`formatProperty`, en-US, like `formatValue` in `web/src/lib/display.tsx`): dropdown labels, currency (the record's `currency_property`, else the quote's currency, else `currency_code`), percentages, prefix and suffix, dates as "December 15, 2026", datetimes in their `timezone` option (else UTC) with the zone, phones formatted, actors as user names.
- `loadPublicQuote` resolves it with `buildQuoteLayout` into `layout` (columns, details, terms, tables as ready-made strings) and each line's `extra` (`{property: text}`), so `src/pdf/quote.ts` and `web/src/public/quote.ts` / `document.ts` draw the same thing. Invoices keep the default columns.
- Fitting: the PDF shares the page width by the widths, wraps every cell and header (headers sit on the rule), and uses 10pt type up to 6 columns, 9pt up to 8 and 8pt beyond, with tighter padding; the header repeats after a page break. Landscape turns the PDF page and widens the public page to 1120px. The public page sizes columns from the widths when they differ from the default, uses smaller type and sideways scrolling beyond 6 columns, and stacks lines on phones with each column's label.

### Meeting booker (`src/calendar/`, `src/routes/booking.ts`, migration 0022)

Visitors book meetings on `/p/book/#<key>` (`web/src/public/book.ts`, its own Vite entry like the quote and form pages). Plan and decisions: `docs/plans/meeting-booker-phase1.md`.

- Calendar connections (`src/calendar/connect.ts`, Settings → Calendars, `web/src/pages/CalendarSettings.tsx`): separate from sign-in. `GET /v1/calendar/{google|microsoft}/connect` (signed-in session only, not API keys) starts an OpenID Connect code flow with PKCE asking for offline access and calendar scopes (Google: `calendar.freebusy`, `calendar.events`, `calendar.calendarlist.readonly`; Microsoft Graph: `Calendars.ReadWrite`, `offline_access`); the callback (`/v1/calendar/{provider}/callback`, skipped by the auth hook) checks the state cookie, that the same user is still signed in, the ID token, the granted scopes and the account's domain (Google: `hd` must be in `CALENDAR_GOOGLE_DOMAINS`, default `profitpad.com`, so the Internal consent screen needs no Google verification; Microsoft: `MICROSOFT_ALLOWED_DOMAINS` if set). It stores the refresh token in `auth.calendar_connections`, encrypted with AES-256-GCM (`src/secret-box.ts`, key `CALENDAR_TOKEN_KEY`); access tokens stay in memory. A user can connect several accounts: all count as busy, the one with `use_for_new_events` gets new meetings. Per connection the user picks the calendars that count as busy (`busy_calendar_ids`, default the main one) and where events go (`write_calendar_id`, default main). A refused refresh token marks the connection `needs_reconnect`. Routes: `GET /v1/calendar/config`, `GET /v1/calendar/connections` (with calendars, fetched live), `PATCH` and `DELETE /v1/calendar/connections/{id}` (delete revokes the Google token). Security log events `calendar.connected`, `calendar.connect_failed`, `calendar.disconnected`.
- Providers (`src/calendar/providers.ts`): Google Calendar `freeBusy` and `events` (`sendUpdates=all`, Meet through `conferenceData.createRequest`); Microsoft Graph `calendarView` (events not `free` and not cancelled count as busy) and `events` (Teams through `isOnlineMeeting`). The provider sends the invite. Base URLs can point at fakes for tests (`GOOGLE_CALENDAR_API_URL`, `MICROSOFT_GRAPH_URL`, `GOOGLE_TOKEN_URL`, `MICROSOFT_TOKEN_URL`, `GOOGLE_REVOKE_URL`).
- Booking pages (object `booking_pages`, `pc_0054`): `host` (user), `duration_minutes` (the default length), `duration_options` (migration 0024: JSON list of the lengths the visitor can pick, 5 to 1440 minutes, at most 12; the write hook sorts it, always adds the default, and stores one length as empty), `slot_step_minutes` (empty: the duration), `buffer_before_minutes`, `buffer_after_minutes`, `min_notice_minutes`, `max_days_ahead`, `daily_limit`, `timezone` (IANA), `availability` (`{"weekly": {"mon": [["09:00","17:00"]], ...}, "overrides": [{"date": "YYYY-MM-DD", "ranges": []}], "rows": [{"days", "start", "end"}]}`, `24:00` allowed as an end; `rows` is how the editor arranged the weekly hours (days `every`, `weekdays`, `weekend` or a day) so it shows them the same way after a save, while `weekly` is what slots are built from), `location_type` (`google_meet`, `teams`, `phone`, `in_person`, `custom`), `location_details`, `form_before_id`, `form_after_id`, `confirmation_message`, `public_key`, `slug` (migration 0023: an address the user picks, `/p/book/#intro-call`, lowercase letters, digits and dashes, 3 to 60, unique ignoring case; public routes find a page by its key or its slug), `status`. The write hook in `booking.ts` checks the time zone, hours and form ids on every write, and refuses `status = published` until the page has a host with a connected calendar, hours, and a published form with the contact email field (before or after). Record page: `web/src/components/BookingPageEditor.tsx` (status and next open times, form pickers, hours editor), the link card and a Calls card. `GET /v1/objects/booking_pages/{id}/check` returns what is missing and the next open times.
- Slots (`src/calendar/slots.ts`, pure, tests in `slots.test.ts`, `npm test`): local hours in the page's zone turned into instants with Intl (daylight saving handled, no date library), stepped by the slot step, minus minimum notice, beyond the horizon, days at the daily limit (meetings booked through the page), and anything whose meeting plus buffers overlaps a busy time. Busy times: every active connection of the host (cached 60 s per host and range) plus CRM calls the host owns with status `scheduled`.
- Public routes: `GET /v1/public/booking/{key}` (page, host name, both forms as `publicDefinition`, theme), `GET .../slots?from&to&duration` (at most 45 days: the page asks for the six weeks its calendar shows; `duration` must be one of the page's lengths, default the default), `POST .../before` (checks the before form's answers, stores nothing), `POST .../phone`, `POST .../book` (`{start, duration, before: {values}, after: {values}, page_url, _hp, _elapsed}`). Same Origin rule, honeypot and fill time as form submissions; rate limits per IP. Booking: answers are checked first; then, in one transaction under `pg_advisory_xact_lock` on the host, the time is checked again with fresh busy times (409 `slot_taken`), each form is applied with `applySubmission` (contact upserted by email with its properties overwritten, ticket if mapped, a form submission), the event is created on the host's calendar with the visitor invited (503 and rollback if that fails), and a `calls` record is created (`call_type` meeting, `status` scheduled, `owner` host, `attendee_name`, `attendee_email`, `meeting_url`, `calendar_provider`, `calendar_event_id`, answers in `body`), linked to the contact, the page and the submissions. If the commit fails after the event was made, the event is deleted. No CRM email is sent: the invite is the confirmation.
- Embedding: `embed.js` turns `<div data-pcrm-booking="<slug or key>">` into the booking flow drawn in the website's own page, like forms (not an iframe), inside a shadow root so the website's CSS and ours stay apart; theme colors are set on the booking's own element. The flow is `web/src/public/book-app.ts` (`mountBooking`), shared with the hosted page (`book.ts`). Requests come from the website, so they need its origin in Settings → Embed domains, the same list as forms: unlisted websites get no CORS headers (the browser blocks the reads, the page says it is not available on this website) and their posts get 403. The link card on the record page shows the address field, link and snippet.
- Cancel and reschedule (migration 0026): every booked meeting gets a random `manage_key` (32 bytes) and keeps `calendar_id` and `calendar_connection_id` so its event can be found later. The link `<UI_URL>/p/book/#manage/<key>` (UI_URL, else the first `CORS_ORIGINS` entry) goes at the end of the invite's description, in the call's body and on the confirmation screen (`manage_url`). Routes: `GET /v1/public/booking/manage/{key}` (meeting and page), `GET .../slots` (the meeting's own time counts as free, and it does not count toward the daily limit), `POST .../cancel` (`{reason?}`: cancels the calendar event so the provider notifies the visitor, Google with `sendUpdates=all`, Graph through the event's cancel action; then the call gets `status` cancelled, `cancelled_at`, `cancel_reason`), `POST .../reschedule` (`{start, duration?}`: under the host lock, checks the new time, moves the event so the provider sends an updated invite, then updates the call's times). Both need an allowed Origin, are limited to 10 a minute per IP, work only on scheduled meetings that have not started, and change the calendar and the CRM together or not at all. Rescheduling needs the page to still be published. The slug `manage` is reserved.
- Not built yet: reminders, team or round-robin pages, provider webhooks, syncing calendar changes back to the call.

### Phone numbers (`src/phone.ts`, migration 0017)

Checked with Google's libphonenumber (`google-libphonenumber` 3.2.47, a packaging of Google's official JavaScript build). Numbers without a country code are read as Canadian (`DEFAULT_REGION = 'CA'`; +1 is shared with the US). Valid numbers are stored as E.164 plus `ext` and the extension, `+16132220328ext4`, and shown as `+1 613-222-0328 ext4` (`displayPhone` in `web/src/lib/display.tsx`, which formats +1 numbers and leaves other countries as stored digits).

- Text properties with `display: "phone"` (allowed by migration 0017; set on contacts, companies and users `phone`) take any format on every write (`toDb` in `src/values.ts`: create, update, batch, import, forms) and refuse invalid numbers with 400. Values stored before 0017 are left as they were until edited.
- Form fields with the phone format store the same form.
- Country pickers: forms (every phone field, generated or custom HTML; the select has no name, so HTML checks ignore it) and CRM phone properties (`PhoneInput` in `web/src/components/ui.tsx`, used by the record page, table cells and the create dialog) show a country picker in front of the number: closed, it shows only the flag (an invisible native select sits on top, so the open list has "🇨🇦 Canada +1" names). The list comes from `GET /v1/public/phone/regions` (public, cached a day: region, calling code, `main` region per code; names from the browser's `Intl.DisplayNames`), via `web/src/public/phone-regions.ts`. The browser never parses numbers: a number typed without + gets `+<code> ` in front (`composePhone`), and libphonenumber drops national prefixes after a code (`+44 020…` is fine). A valid number on a form is rewritten to the display form and the picker follows its region.
- Write errors from `toDb` carry `details.property`; the record page shows a refused value's error under that property and keeps the refused text in the box (not saved, not resent unchanged), the create dialog shows it under the field, and the table cell editor keeps its editor open with the error.
- `POST /v1/phone/validate` (API key, read scope; in the docs under Utilities): `{number, region?}` returns `{input, valid, value, display, e164, extension, region, type, reason}`; invalid numbers are `valid: false` with a reason, not an error.

### File storage (`src/files.ts`, migration 0025)

Files are stored on the API server's disk for now (moving to Cloudflare R2 later: `docs/plans/file-storage.md`). A file record (`files`, `pc_0050`) holds `name`, `mime_type`, `size_bytes`, `storage_key`, `checksum` (`sha256:...`), `status` (`uploading`/`ready`) and `public_token`; migration 0025 adds the last two and makes all six read-only, so only the file endpoints write them (a `storage_key` written through a record update could point at another file's bytes). Bytes live under `FILES_DIR`: `blobs/<last 2 chars of id>/<id>` when complete, `uploads/<id>.part` while chunks arrive.

- Upload: `POST /v1/files/uploads` `{name, size, content_type?, object?, record_id?, property?}` makes the record (status uploading) and returns `chunk_bytes` (8 MB); `PUT /v1/files/{id}/content?offset=` (application/octet-stream) appends one chunk at the current position (409 with `details.received` otherwise); `GET /v1/files/{id}/upload` says where to resume. Only the uploader sends chunks. The last chunk computes the checksum and moves the file into place. With a target record and file property the caller needs edit access to it and the property must have room (`max_files`); otherwise Create on files. Max size `FILES_MAX_BYTES` (default 5 GB).
- Attaching: a normal record update adds the id to a file property. `planWrite` (`records.ts`) calls the check `files.ts` registers with `onFilePropertyWrite`: every newly added id must be a ready, active file the caller can already open or uploaded themselves, so linking a file to a record never grants access to it.
- Who can open a file: admins and unrestricted keys; the uploader; anyone with Read on files and record access to the file record; anyone who can read a record (active or archived) whose file property holds it, unless that property is hidden from them (`canAccessFile`). Publishing and unpublishing use the same rules with edit access. Files the caller cannot open look like files that do not exist (404).
- Reading by script: `GET /v1/files/{id}/content` returns the bytes of a ready file the caller can open, up to 25 MB (`CONTENT_MAX_BYTES`), streamed by the API (not X-Accel-Redirect, so the CORS headers survive) as an attachment with the sandbox CSP. The CRM page uses it to hand files to custom views.
- Opening: `GET /v1/files/{id}/url[?download=1]` returns a signed link `/v1/files/{id}/raw?d=&exp=&sig=` (HMAC-SHA256 with `FILES_URL_KEY`) that works without sign-in until `exp`: the next hour boundary plus an hour, so the same link is handed out for the whole hour and browsers reuse their cached copy (`Cache-Control: private, max-age=<until exp>`). Archived files do not open.
- Public links: `POST /v1/files/{id}/public` sets a random `public_token`; `/files/<token>/<name>` then opens for anyone (`Cache-Control: public, max-age=86400`; the name part is cosmetic). `DELETE` clears it and the link stops at once. Looked-up public files are kept in memory for a minute (up to 1000), so a busy link does not query the database on every request.
- Safety: files are served from the API's domain, where the session cookie lives. Only images (not SVG), video, audio, PDF and plain text are sent `inline`, with a strict CSP (`default-src 'none'`, media and images from the file's own origin); everything else, HTML and SVG included, is an `attachment` with `Content-Security-Policy: sandbox; default-src 'none'`. Every file response has nosniff. Inline media gets no `sandbox` because Chromium's built-in video viewer cannot load the video inside a sandboxed page (found in the browser 2026-11-02); browsers show media in their own viewers, which run no script from the file. The global `onSend` hook in `server.ts` keeps a CSP a route set itself.
- Serving and caching: with `FILES_ACCEL_PREFIX` set (production) the API answers with `X-Accel-Redirect` and nginx sends the bytes (`location /_pcrm_files/` in `deploy/nginx-api.test-crm.profitpad.com.conf`): sendfile, range requests, `open_file_cache` for files opened at least twice in 10 minutes, and the OS page cache for hot bytes. Without it (local dev) the API streams the file itself with ETag and single byte ranges; the Vite dev server forwards `/files/` to the API as well as `/v1`, since public links are built on the origin the request came from.
- Cleanup (`startFileSweeper`, a minute after start, then hourly): uploads not finished within a day are deleted for good with their partial bytes, and bytes whose record is gone or permanently deleted are removed (`meta.delete_record` clears `storage_key`, so the id in the path is what links them).
- UI: file properties on record pages (`web/src/components/FileField.tsx`: list, open, download, remove, upload with progress), an Upload files button on the Files list in place of Create (`FileUploadButton.tsx`, files with no record; needs Create on files; one file opens its page, several refresh the list), a File card on file records (`FileCard.tsx`: preview for images, video and audio, open, download, public link), file properties can be created in Settings → Properties (with "Most files per record"), and tables show "2 files". Client helpers in `web/src/lib/files.ts` (chunked upload with retries and resume).

### Admin approval (`src/approval.ts`, migration 0061)

Places CRM data goes (view integrations, webhook endpoints and subscriptions, embed domains) can be set up by anyone who may manage them, but only an admin signed in to the CRM in a browser can turn one on (`canApprove`: a session, no OAuth app, no API key, admin). The rule is in the API, so it holds for MCP clients and API keys alike.
- Set up over MCP or with an API key, an integration, endpoint or subscription starts off with `awaiting_approval` true and `requested_by`, `requested_via` (the connected app's name, or "API key") and `requested_at` set, whatever `enabled` said. An update from them that asks to turn one on fails with 403 `approval_required` and `details.approve_url`; turning one off always works.
- Changing where an enabled one sends data, or what it sends, from outside the CRM turns it off and back to waiting: integrations on `url` or `audience`, endpoints on `url`, subscriptions on anything but `description`. Other edits leave it as it is.
- An admin approves by turning it on (Settings: "Approve and turn on"), which needs a recent sign-in (`requireRecentSignIn`), clears `awaiting_approval` and stamps `approved_by` / `approved_at`. Logged as `integration.approved`, `webhook.endpoint_approved` and `webhook.subscription_approved`.
- Embed domains: `ui.settings` key `forms` holds `allowed_origins` and `pending_origins` (`{origin, requested_by, requested_via, requested_at}`). `PUT /v1/ui/settings/forms` (`saveEmbedDomains` in `src/routes/ui.ts`) saves the list as given from an admin in the CRM (`pending_origins` given: the waiting ones to keep); from anywhere else removals apply and new websites go to `pending_origins`. Only `allowed_origins` is checked by the public form and booking routes. Logged as `embed_domain.requested` and `embed_domain.approved`.
- Admin outputs carry the approval fields plus `approve_url` while waiting: `UI_URL` + `/settings/view-integrations?review=<key>`, `/settings/webhooks?review=endpoint-<id>` or `subscription-<id>`, `/settings/embed-domains?review=pending`. The Settings pages scroll to and highlight the item (`useReview` and `ApprovalNote` in `web/src/components/settings.tsx`). MCP results add a `next_step` asking the AI to hand the link to the admin; MCP `list_embed_domains` and `add_embed_domain` cover embed domains.
- Rows that were already on before 0061 stay on.

### Card scanner (`src/card-scan.ts`, `src/card-parse.ts`, `web/src/pages/CardScanner.tsx`, migrations 0063 and 0065)

`/scan` in the UI (menu item type `card_scanner`, and a Scan card button on Contacts). In the browser (`web/src/lib/card-image.ts`): with the Claude reader the photo is uploaded as taken and read, Claude also returns the card's four corners (fractions of the photo, checked by `cardCorners` in `card-scan.ts`: clockwise, convex, at least 4% of the photo), and the page straightens the card from them, 4% further out on each side so the card's real edges show (`CLAUDE_CROP_MARGIN`), and uploads that as the contact's `business_card` photo while the person reviews (the scan record keeps the photo as taken). With Tesseract the person drags the corners first (starting from an inset frame), the straightened card is uploaded, and a black-and-white, contrast-stretched copy (inverted for dark cards) goes along in the read request and is not stored. On the review screen "Adjust corners" (on hover, a button on touch screens) re-cuts the saved photo from new corners without reading the card again. There is no automatic corner finder in the browser: the one first built often missed the card.

API: `GET /v1/card-scans/setup` (active reader, recent events for Trade Show Mode, permissions), `POST /v1/card-scans/read` (`file_id`, optional `ocr_image`; returns fields and matching contacts and companies), `POST /v1/card-scans/match` (matches again after edits), `POST /v1/card-scans/save` (new contact, or blanks filled on an existing one; company linked or created by domain; with an event, a `marketing_event_participations` record with `priority`, `follow_up_status`, `follow_up_date`, `notes`; otherwise the note becomes a `notes` record). Admins: `GET`/`PUT /v1/card-scans/settings`.

Usage: every read is a `card_scans` record (`pc_0056`, migration 0067): reader, model (the one that answered), outcome (read, not a card, failed, with the error), input/output/cache tokens, estimated cost (`PRICES` in `card-scan.ts`, Anthropic list prices; null for a model not listed), seconds, the card photo, and `saved_as` (new or updated contact, empty when never saved). Failed Claude reads that got an answer still record their tokens. Every property is read-only: the scanner inserts and updates the table directly, so a scan is logged whatever the scanning person's roles say about card_scans, and nobody edits the numbers. Saving links the scan to its contact, company, event and participation (card scans may link only to those four). `created_by` is the person who scanned. The "Card scanner usage" custom view (`/view/#card-scanner-usage`) reports it by month, person, model and event.

Readers (`auth.card_scan_settings`, one row): `tesseract` (default; the `tesseract` program in the API container, sparse-text mode, TSV words grouped into lines, then `card-parse.ts` rules) or `claude` (the tenant's Anthropic key, sealed with `secret-box.ts`, only the last four characters shown; always Claude Haiku 5.5, no model to pick: Opus 5.5 read no better in scripts/card-bench at about 40 times the cost; the `claude_model` column in `auth.card_scan_settings` is no longer read; JSON schema output). Without either, people type the details in. Accuracy on synthetic cards: `scripts/card-bench/README.md`.

### Currencies and exchange rates (`src/currency.ts`, `src/currency-rates.ts`, migration 0068a)

- **Current rates** live on the registry `meta.pc_0007`: `rate_to_base` is what 1 unit is worth in the base currency (`is_base`, exactly one, always rate 1, cannot be archived: trigger `base_rules`), plus `rate_date`, `rate_source` (`manual`/`provider`) and `rate_manual` (pinned by an admin in automatic mode).
- **History**: `meta.currency_rates`, one row per (`from_code`, `to_code`, `rate_date`): 1 from = `rate` to, `to_code` always the base in effect that day, `source` manual or provider (with `provider`). It holds the rate the CRM used each day: a typed rate replaces that day's fetched row, and a fetch of an unpinned currency replaces that day's typed row. The API can insert and update, never delete.
- **Settings**: `meta.currency_settings` (one row): `mode` manual or automatic, `schedule` (`daily`, `every_2_days`, `weekly`, `every_14_days`, `monthly`, `quarterly`), `provider`, and the last lookup's time, status (`ok`, `partial`, `failed`) and error.
- **Conversion in SQL**: `convert_currency(amount, from, to default base, on_date default null)` and `currency_rate(from, to, on_date)`, in both `view_data` (allowed in custom view queries: `meta._view_function_allowed` lists them) and `reporting`. No date: the current rates. A date: the latest history row on or before it (the earliest row when the date is before any history); the pivot is the base of the latest row that day, so days before a base change still convert through the old base. Null when a rate is unknown. Views `view_data.currency_rates` / `reporting.currency_rates` expose the history; `currencies` gained the rate columns. Documented for view builders in the guide's sql topic ("Money in different currencies"), and the schema topic marks money properties.
- **Lookups**: providers in `src/currency-rates.ts` (`PROVIDERS`: `frankfurter` default, `ecb`), each answering "1 base = x code" for a list of codes. `fetchRates` stores every active, non-base, unpinned currency; codes the provider lacks make the status `partial` (named in `last_error`) and still count as done for the schedule. Choice of provider: `docs/currency-rates.md`.
- **Scheduling**: an API timer (`startCurrencyScheduler`, first check 2 minutes after start, then hourly) runs `fetchRates` when due. Due is counted in UTC days from `last_success_at` (N days later, or the 1st of the next month or quarter), so restarts do not matter, and `pg_try_advisory_xact_lock` keeps two API containers from fetching at once. Chosen over n8n because it needs no workflow or key to set up per tenant and keeps working when n8n is down; `POST /v1/currency-rates/fetch` with `{"if_due": true}` and an admin key lets n8n drive it instead if wanted. A failed lookup is retried at the next hourly check.
- **API**: `GET/POST /v1/currencies`, `PATCH /v1/currencies/{code}` (`rate_to_base` sets a rate, pinning it in automatic mode; `rate_manual: false` unpins and looks it up; archive/restore), `GET/PUT /v1/currency-settings` (a base change re-expresses every rate through today's rates and writes history rows against the new base; turning automatic on, or changing provider or base while on, looks up at once), `POST /v1/currency-rates/fetch`, `GET /v1/currency-rates` (history), `GET /v1/currency-rates/convert`. Adding a currency also adds it to every currency dropdown that money properties point at (`currency_property`), unless `add_to_dropdowns: false`. Changes are logged as `settings.updated`.
- **UI**: Settings → Currencies (`web/src/pages/CurrencySettings.tsx`, Workspace group): base currency, manual or automatic, schedule and provider, last and next lookup with "Look up rates now", the currency table (rates as "1 base = x"; set or pin a rate, use the looked-up rate again, archive), Add currency (name and decimals from the browser's `Intl` data), and the rate history.

### Webhooks (`src/webhooks.ts`, `src/routes/webhooks.ts`, migration 0038)

Admins send record events to outside URLs. An endpoint (`auth.webhook_endpoints`) is a URL (https on a public address; hosts in `INTEGRATION_PRIVATE_HOSTS` may use http and private addresses, checked again at connect time by `guardedLookup` from `src/integrations.ts`), an optional secret header (e.g. n8n header auth) and a signing secret (`whsec_...`); both secrets are sealed with the secret box (`CALENDAR_TOKEN_KEY`). Each endpoint has subscriptions (`auth.webhook_subscriptions`): one object (any `crm` object: contacts, forms, form submissions, views, users, custom objects...) and one event:

| event | fires when | extra fields |
|---|---|---|
| `created` | a record is inserted | |
| `updated` | any property value changes (not on create; not archive/restore/merge status), optionally only when one of `properties` changes; one event per transaction listing every change | `changes: [{property, old_value, new_value}]` |
| `merged` | a record is merged into this one; `record_id` is the winner | `merged_ids` |
| `archived` / `restored` | `record_status` active to archived / archived to active | |
| `association_added` / `association_removed` | a link to another record is added or removed, once per label, optionally only to `target_object` and/or one `label_id` | `association: {object, record_id, label_id, label, association_id}` |
| `property_changed` | one of `properties` becomes non-empty (populated or changed; also on create when given a value), once per property | `change` |
| `property_cleared` | one of `properties` becomes empty | `change` |

Plus optional `filter_groups` (same format and compiler as record search, `compileFilterGroups`): the WHERE part. And optional `send_properties` (up to 3, migration 0040): the properties whose current values each delivery carries; with none, deliveries carry no property values. The summary sentence (`summarize`) renders it SQL-like, e.g. `When a contact's email is populated or changed WHERE first_name contains 'chris'`. Filters are checked against the record as it is when the worker processes the event (normally a few milliseconds after the change commits), not the exact state at the change; for `merged` they are checked on the winner.

- Capture: nothing new is written per change beyond what `meta.record_history` already records (its triggers cover the API, merges, line cascades, imports, calculations and raw SQL). A statement-level trigger on `meta.record_history` (`meta.tg_webhook_capture`) copies the rows of objects that have an enabled subscription on an enabled endpoint into `meta.webhook_outbox`, with `txid_current()`. Rows become visible only when the writing transaction commits, so no change is skipped because of commit order. Changes made with `crm.skip_history` on (permanent delete) are not captured; permanent delete is not an event.
- Worker (`startWebhookWorker`, in the API process): woken at once by `NOTIFY webhook_outbox`, which the capture trigger sends and Postgres delivers when the writing transaction commits (0041; the worker LISTENs on a connection of its own outside the pool, `newClient` in `src/db.ts`, reconnecting after a second if it drops), when a send finishes, when a delivery is retried, and every 500 ms as a fallback (due retries, a lost listener). It takes whole transactions from the outbox (`for update skip locked`, so the API role needs update on it), groups rows by transaction and record, builds the events per subscription, applies filters (one query per subscription), reads every affected record once and inserts `auth.webhook_deliveries` with the payload, all in one transaction. Then it puts waiting deliveries into batches (`formBatches`, migration 0042): per endpoint in id order, a batch closes when it holds the endpoint's `batch_max` events (1 to 1000, default 10) or 5 MB, or 50 ms after its first event was queued (a timer wakes the worker then), and gets a `batch_id`. Then it claims due batches (a 2-minute lease, so a crash just retries them) and starts the POSTs without waiting for them (up to 32 in flight across all endpoints), so a slow receiver never holds up new events or other endpoints. Measured on the local test cluster: the POST reaches a receiver 52 to 58 ms after the API answers the write (the batch window; 3 to 12 ms before batching), also while another endpoint takes 8 seconds to answer; with the listener cut, up to about 0.25 to 0.4 s until it reconnects.
- Delivery: one `POST` per batch, also for a single event: JSON `{batch_id, endpoint_id, attempt, sent_at, events: [...]}`, the events in the order they were queued. Each event is `{id, event, object, object_type_id, record_id, occurred_at, changed_by, source, subscription_id, endpoint_id, record, ...extra}` where `record` is `{id, object_type_id, record_status, properties}` and `properties` holds only the subscription's `send_properties` that are still active (empty when none are chosen; no permission filtering: webhooks are admin-only), or null with `record_omitted` above 256 KB. Event `id`s and the `batch_id` are the same on retries (de-duplicate on the event id). Headers: `X-PCRM-Batch-Id`, `X-PCRM-Event-Count`, `X-PCRM-Delivery-Attempt`, `X-PCRM-Signature: t=<unix>,v1=<hex HMAC-SHA256("<t>.<body>")>`, the secret header. 2xx within 10 seconds is success for the whole batch; otherwise the batch is retried after 1, 5, 30, 120, 360, 720 and 1440 minutes, then `failed` (Retry in Settings or `POST /v1/webhooks/deliveries/{id}/retry`, which brings back every failed event of that batch, batched again). The log stays one row per event (`auth.webhook_deliveries`, `batch_id` groups them; Settings shows it per row). The endpoint keeps `last_success_at`, `last_failure_at`, `last_error` and `consecutive_failures`. A disabled endpoint keeps its pending deliveries and sends them when enabled again. Deliveries are kept 30 days (hourly sweep). Order between deliveries is not guaranteed; use `occurred_at`.
- A receiver that writes back to the CRM can trigger its own subscription again (no loop protection); `source` and `changed_by` in the payload tell such writes apart.
- Access: admins only (`requireAdmin`); OAuth tokens (an admin's AI over MCP) need the schema scope. Browser changes to endpoints and secrets need a recent sign-in. Revealing a signing secret is for people only (not OAuth tokens). Every change is in the security log (`webhook.*` events, never secrets).
- REST: `/v1/webhooks/events`, `/endpoints` (CRUD, `/{id}/secret`, `/{id}/rotate-secret`, `/{id}/test`), `/subscriptions` (CRUD; endpoint and object fixed after create), `/deliveries` (the sent log: list with `endpoint_id`, `subscription_id`, `status`, `event`, `object`, `record_id`, `since`, `until`, `before`, answering `results`, `next_before`, `totals` per status for the same filters except status and paging, and `kept_days`; detail with payload; retry). In the OpenAPI doc under Webhooks.
- MCP (schema scope): `list_webhooks`, `create_webhook_endpoint` (returns the signing secret once), `update_webhook_endpoint`, `delete_webhook_endpoint`, `test_webhook_endpoint`, `create_webhook_subscription`, `update_webhook_subscription`, `delete_webhook_subscription`, `list_webhook_deliveries`. The admin instructions tell the model to confirm URLs and subscriptions with the admin before changing them. The user chose to let the AI create endpoints too (unlike view integrations, which only people add).
- UI: Settings → Webhooks (`web/src/pages/WebhookSettings.tsx`): endpoints as cards with health, Edit, Send test, Reveal secret, New secret, Turn off/on, Delete; each endpoint's subscriptions (summary sentence, edit, on/off, delete) and an add/edit form (object, event, properties, link target and label, up to 3 values to send, WHERE conditions with `FilterBuilder`); Recent deliveries per endpoint (status filter, payload, Retry) and a page-wide Sent log for the last 30 days (filters for status, endpoint, event, object and record, date range; totals per status). `list_webhook_deliveries` on the MCP takes the same filters. Index `webhook_deliveries_record_idx` (0040) serves the record filter.
